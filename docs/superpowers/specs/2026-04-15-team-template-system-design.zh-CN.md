# Win Together 团队模板系统设计稿

日期：2026-04-15
状态：提议中

## 1. 设计摘要

`Win Together` 需要把团队组建从“写死在代码里”改成“由模板文件驱动”。

系统应支持三层结构：

1. 内置固定团队模板
2. 用户自己创建或由 AI 生成的新模板
3. 运行某个 mission 时的临时覆盖配置

默认用户流程仍然要保持轻量：

- 用户打开 `Win Together`
- 用户输入目标
- 系统默认使用一个预设团队模板
- 如果用户没有特别切换，就不额外增加配置步骤
- `Captain` 仍然负责实际调度，但团队成员、默认职责、初始 prompt 等基础信息来自模板文件

这样既能保持当前版本的易用性，也能为后面“AI 自动生成团队模板”打基础。

## 2. 设计目标

### 2.1 主要目标

- 不再把团队成员写死在 runtime 代码里
- 让团队配置变成可查看、可编辑、可复用的文件资产
- 让 AI 以后可以直接生成模板文件，而不是改代码
- 保持当前第一版“直接输入目标就能开始”的轻量体验
- 为后续前端团队、游戏开发团队、测试团队等不同团队形态预留空间

### 2.2 第一版不做的事

- 不做完整的可视化模板编辑器
- 不做模板云同步和多人共享
- 不做任意脚本化模板逻辑
- 不在这一轮就做完整的“AI 模板生成 UI”

## 3. 推荐的用户模型

系统第一版应该先采用“默认模板自动生效”的模式，而不是一上来强迫用户选模板。

这样做的原因是：

- 首次使用依然简单
- 高级用户需要时再去切换模板
- 以后加“AI 生成模板”也不会破坏当前启动流程

所以最终模型应该是：

- 有一个默认模板，平时直接用
- 有一个模板库，供用户后续切换
- 未来 AI 生成的新模板也保存在同一个模板库里
- 某次 mission 如有特殊需要，可以在运行时做少量覆盖

## 4. 模板存储结构

团队模板建议存放在现有记忆系统附近，作为长期可追踪的配置资产。

推荐目录：

```text
WIN_MEMORY/
  teams/
    INDEX.md
    templates/
      default-software-team.json
      frontend-team.json
      game-dev-team.json
      generated/
        <template-id>.json
```

这样做的好处是：

- 模板与项目记忆体系放在一起，容易管理
- 方便以后做版本记录和 AI 生成
- 用户也能直接查看模板文件长什么样

## 5. 模板文件结构

第一版建议使用结构化 `JSON` 文件。

推荐字段大致如下：

```json
{
  "id": "default-software-team",
  "name": "默认软件开发团队",
  "description": "Captain 主导的通用软件开发团队。",
  "version": 1,
  "captain": {
    "name": "Captain",
    "role": "captain",
    "status": "planning",
    "prompt": "负责理解目标、拆解任务、组织协作和总结结果。"
  },
  "workers": [
    {
      "id": "researcher",
      "name": "Researcher",
      "role": "researcher",
      "defaultStatus": "running",
      "prompt": "负责调研、分析代码和识别风险。"
    },
    {
      "id": "builder",
      "name": "Builder",
      "role": "builder",
      "defaultStatus": "idle",
      "prompt": "负责实现修改并汇报结果。"
    }
  ],
  "runtime": {
    "allowDynamicExpansion": true,
    "defaultActiveWorkers": ["researcher", "builder"]
  }
}
```

第一版字段不要做得太复杂，先保留这些核心内容：

- 模板 ID 和名称
- `Captain` 的定义
- worker 列表
- 每个角色的默认职责和 prompt 片段
- 轻量 runtime 策略

这样既够用，也方便未来扩展。

## 6. 运行时的解析规则

以后 runtime 在启动 mission 时，不应直接用代码里的固定团队，而要按下面顺序处理：

1. 加载默认模板
2. 如果用户手动选了模板，则覆盖默认模板
3. 如果本次 mission 有临时覆盖配置，再叠加到模板结果上
4. 根据最终结果创建 `Captain` 和 worker 记录
5. 按这个模板驱动的团队去发布 `agent.spawned` 等事件

这样整个过程会更稳定，也更容易追踪。

## 7. Captain 与模板的关系

模板不是替代 `Captain`，而是定义“初始团队形态”。

也就是说：

- 模板决定一开始有哪些角色
- 模板决定这些角色的默认名字、状态和职责
- `Captain` 仍然负责调度和组织协作
- 如果模板允许动态扩编，那么 `Captain` 后续仍然可以继续加人

所以：

- 模板负责“团队初始配置”
- `Captain` 负责“团队运行时指挥”

## 8. AI 生成模板的未来路径

后面 AI 生成模板时，应该直接复用这一套文件体系，而不是另起炉灶。

理想流程是：

1. 用户描述想要什么团队
2. 系统调用 `Codex` 或其他模型生成一份模板文件
3. 系统校验模板格式是否合法
4. 保存到 `WIN_MEMORY/teams/templates/generated/`
5. 这个模板立刻进入模板库，可以被选用

所以现在先把模板文件结构设计好，后面 AI 生成就会非常顺。

## 9. 第一版如何接进产品

第一版模板系统的接入方式应该尽量轻，不要把当前首页搞复杂。

推荐方式：

- 系统始终有一个默认模板
- 用户启动任务时默认直接使用它
- 不强制用户先选模板
- 以后再把模板切换能力作为一个可选入口补进首页或设置页

这样既完成了架构升级，也不会破坏当前产品的轻量入口。

## 10. 测试层面的影响

第一版引入模板系统后，至少要补这些验证：

- 模板文件能否正确加载
- 模板格式错误时是否有清晰报错
- runtime 能否根据模板生成 Captain 和 worker
- `Team Room` 成员列表能否显示模板驱动的角色
- 默认模板模式下，首次使用路径仍然正常

浏览器 bridge 里的 stub 数据也要逐步改成模板驱动，这样浏览器回归和 Electron 真链路的概念才一致。

## 11. 验收标准

如果下一阶段实现完成，至少应该满足这 5 条：

1. 系统能从磁盘加载默认团队模板
2. 系统能用模板生成 `Captain` 和 worker
3. `Team Room` 里显示的成员来自模板，不再是硬编码
4. 用户仍然可以不增加额外步骤就直接开始 mission
5. 后续 AI 生成模板有明确接入路径

## 12. 决策总结

- 使用文件模板，而不是把团队写死在代码里
- 第一版用 `JSON` 作为模板格式
- 默认先用隐藏的默认模板，保证入口足够轻
- 未来 AI 生成模板时，直接保存到同一套模板库
- `Captain` 仍是运行时调度核心，模板只负责定义初始团队结构
